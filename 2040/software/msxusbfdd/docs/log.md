# Change Log

## PicoVerse 2040 MSXUSBFDD v1.01

- Version bumped to v1.01 (top-level, `msx/` and `tool/` Makefiles, the tool's fallback `APP_VERSION`, and the firmware program version in `pico/msxusbfdd/CMakeLists.txt`, now `1.01`).
- Moved the RP2040 firmware build from Pico SDK 2.2.0 to Pico SDK 2.3.1 (including its bundled TinyUSB), from the Arm GNU Toolchain 14.2.Rel1 to 15.2.Rel1 (GCC 15.2.1) and from picotool 2.2.0-a4 to 2.3.1. `pico/msxusbfdd/CMakeLists.txt` now sets `sdkVersion 2.3.1`, `toolchainVersion 15_2_Rel1` and `picotoolVersion 2.3.1`. These are expected under `~/.pico-sdk/sdk/2.3.1`, `~/.pico-sdk/toolchain/15_2_Rel1`, `~/.pico-sdk/picotool/2.3.1` and `~/.pico-sdk/tools/2.3.1` (pioasm). The old `pico/msxusbfdd/build` directory must be removed once so CMake reconfigures (`make clean` does this).
- Clean `make all` build succeeds with no source changes; the `-Wl,--wrap=hcd_*` / `hw_endpoint_reset_transfer` TinyUSB hooks still link against SDK 2.3.1. `dist/msxusbfdd.bin` went from 52672 to 50808 bytes. Rebuilt the BIOS ROM (banner shows `v1.01`), the embedded firmware/ROM headers, `tool/dist/msxusbfdd.exe` and `tool/dist/msxusbfdd.uf2` (the UF2 is regenerated by running the tool, since `make` clears `tool/dist`).
- Host tests pass (`make test`): 177 filesystem and 101 Z80 checks. They do not exercise the firmware or TinyUSB, so the new SDK and compiler still need a hardware check (USB enumeration, floppy and storage access on a real MSX) before release.

## PicoVerse 2040 MSXUSBFDD v1.00

- Rolled back the implementation, build metadata, tests, and distributed firmware/tool/UF2 from v1.01 to the last pre-v1.01 revision (`4f3d801`) following hardware regressions. This restores the historical v1.00 behavior, not a new UF000x fix.
- Rollback validation: BIOS/Pico/tool build succeeds; 177 filesystem and 101 Z80 checks pass. Distributed firmware, embedded headers, tool and UF2 are restored byte-for-byte from `4f3d801`; picotool confirms the RP2040 family and original 1.0 firmware metadata.

- First release: port of the MSXUSB USB FDD BIOS (Rookie Drive / Konamiman NestorBIOS based, CH376S version) to the PicoVerse 2040. The CH376S is replaced by the USB host of the RP2040 (TinyUSB), the Z80 side no longer talks to a USB host chip.
- New aggregate `Makefile` with the `msx`, `pico`, `tool`, `test` and `clean` targets, following the other 2040 packages (`msx/`, `pico/msxusbfdd/`, `tool/`).
- MSX BIOS (`msx/`): the 32KB ROM (MSX-DOS 1 kernel in bank 0, driver in bank 1, Konami SCC mapper style 8KB banking at 5000h/7000h) is assembled with sjasm (`msx/tools/sjasm.exe`) into `msx/dist/msxusbfdd.rom`. The kernel, DSKIO/DSKCHG, FORMAT, boot menu, DSK image management and the `CALL USB*` commands are unchanged.
- MSX BIOS: `bank1/ch376.asm` was replaced by `bank1/pico.asm` (same `HW_*` and `HWF_*` routines and contracts) and `bank1/usb.asm` was rewritten: the Z80 USB stack (enumeration, hub handling, CBI transport, descriptor parsing) is gone, `USB_INIT_DEV` asks the firmware for the type of the connected device and `USB_EXECUTE_CBI` sends the 12 byte UFI command to it. The EP0 diagnostics (`diag_ep0.asm`) were removed. The boot banner and error messages were updated and show the version (generated into `msx/build/version.asm` by `msx/Makefile`).
- Mailbox (`msx/src/pico_regs.asm`, `pico/msxusbfdd/mailbox.h`): memory mapped registers at 7D00h-7FCFh of the cartridge slot (256 byte data window paged over an 8KB buffer, status, result, page, command, 16 argument bytes, 16 response bytes, "PVFD" signature). The MSX writes the command and polls the BUSY bit; CAPS+ESC (panic button) aborts the running command.
- Firmware (`pico/msxusbfdd/`): core 0 serves the MSX bus (32KB ROM copied to SRAM, Konami SCC mapper, mailbox registers), core 1 runs the TinyUSB host and the commands (`usb_host.c`).
- Firmware: USB floppy drives are handled by an application class driver for the UFI subclass (CBI with interrupt, CBI without interrupt and Bulk-Only protocols). Failed commands get their sense data with REQUEST SENSE and the ASC/ASCQ is returned to the BIOS, like the Z80 code did. The RP2040 host driver cannot abort transfers nor clear stalls, so the data toggles are reset with CLEAR_FEATURE(HALT) on all endpoints and by reopening them.
- Firmware: USB flash drives (SCSI Bulk-Only) use the TinyUSB MSC driver and FatFs R0.15 (`fatfs/`, short 8.3 names, FAT12/16/32, 512 byte sectors) to emulate the file commands of the CH376 (`fs_service.c`): mount, open file/directory with a current directory, create, make directory, delete, enumeration of raw 32 byte directory entries with `*`/`?` patterns, seek, read, write and attributes. Open files are flushed after 300 ms without commands and when closed.
- Firmware: devices connected through hubs are supported by the TinyUSB hub driver, the BIOS shows "USB hub found".
- Tool (`tool/`): `msxusbfdd.exe` embeds the firmware and the BIOS ROM and creates `msxusbfdd.uf2` (firmware followed by the ROM, which the firmware finds after its own binary). `-r` uses another 32KB ROM and `-o` sets the output name.
- Tests (`tests/`): `make test` runs both host tests. The file service test checks the FAT12/FAT16/FAT32 RAM disks (177 checks). The Z80 test (`make -C tests z80test`) runs the real BIOS ROM in a Z80 emulator against the real file service and an emulated mailbox and floppy drive (95 checks: HWF_* routines, enumeration, reads and writes, UFI commands, panic button, device change).
- Firmware robustness (after review): a control transfer that times out is left running instead of being aborted (the RP2040 host driver can't cancel it, the next command waits for the control pipe); a timeout on the flash drive drops the device until it is connected again; a failed REQUEST SENSE is reported as a generic error (ASC 44h) instead of success; closing a file reports flush errors.
- TEAC USB UF000x (0644:0000, UFI/CBI with an interrupt endpoint at 83h that never reports the command status) failed the INQUIRY at boot. The CBI status stage now waits only 2 s for the interrupt endpoint until it proves to work; a drive that doesn't answer twice is handled as a CB drive (no status stage) and remembered while the firmware runs. The 0644:0000 drive is preset as CB (same quirk as Linux). In CB mode the data toggles are cleared after the timeout, and commands without data, writes and short reads are checked with REQUEST SENSE since there is no status. The TEAC FD-05PUB keeps using the interrupt status.
- Diagnostics: when the INQUIRY at boot fails the BIOS prints `Diag: PP FF SS EE XX RR NN SA SB CC` from new `PV_CMD_DEV_INFO` response bytes 6-15: protocol, flags and, for the first transfer of the last command that did not succeed, the stage (command block, data, status, sense, recovery), endpoint, transfer result, USB error, bytes transferred and the raw RP2040 SIE status flags (toggle error, stall, NAK, RX timeout, CRC...), plus the number of failed commands. The first failure is kept because the recovery that follows a timeout (bus reset, CLEAR_FEATURE) would otherwise overwrite it. Z80 test updated.
- TEAC UF000x behind a hub: the diagnostics showed the INQUIRY data stage (bulk IN 82h) NAKed until the timeout while the command block was accepted; without the hub the INQUIRY works. The "TEAC 0644:0000 is CB" preset was removed: Linux only applies it to bcdDevice 1.00 and the ID is shared by other TEAC drives (it could have changed the FD-05PUB); only drives that fail to report the status twice are handled as CB. Two changes aimed at drives that are still initializing or wedged: the first command is held back until 3 s after the enumeration (`UFI_SETTLE_MS`), and the recovery after an error (bus reset) now sends the CB/CBI reset (class command block with SEND DIAGNOSTIC, like Linux) before clearing the endpoint halts.
- TEAC UF000x test results: via a hub the INQUIRY data stage timed out three times, then TEST UNIT READY worked (so the interrupt status endpoint works on this drive) and READ CAPACITY timed out at the data stage; connected directly the INQUIRY and TEST UNIT READY (ASC 28h, media changed) worked and READ CAPACITY timed out at the command block (the drive NAKs the control transfer). Commands that touch the disk or follow a media change are slow, so the 5 s wait was too short: the timeout of a transfer is now 30 s (`TIMEOUT_NORMAL_MS`) and the wait for the interrupt status of a CBI drive that hasn't proven it works is 8 s. The CB reset after errors was removed (it didn't help and could disturb a drive that is still busy). The `Diag:` SB byte is now the duration of the slowest transfer in 100 ms units, to show how long the drive needs.
- TEAC UF000x capture (USBPcap on the PC, same drive and hub): Windows sends SET_INTERFACE (alternate setting 0) right after SET_CONFIGURATION and the drive answers the first INQUIRY immediately; a failing command is signalled by a STALL of the command block (the interrupt status is always 0000); READ FORMAT CAPACITIES (the first command after a media change) takes about 0.6 s; and even Windows needed three tries, 5 s apart, for the first READ(10) after the media change (transaction errors). The firmware now sends SET_INTERFACE after SET_CONFIGURATION (the drive is reported to the BIOS when it completes), the settle delay before the first command is 500 ms, the transfer timeout is 10 s and the interrupt probe wait 3 s. The boot self test now follows the Windows order (TEST UNIT READY, READ FORMAT CAPACITIES, READ CAPACITY) and prints the first 8 data bytes. The earlier READ CAPACITY-first order, which the BIOS never uses, was what timed out in the direct connection test.
- The RP2040 host driver of TinyUSB calls `panic()` on a data toggle error, which would hang core 1 for good and leave the MSX waiting for the mailbox forever (an MSX freeze): the data sequence error interrupt is now disabled after `tuh_init()`, so a toggle error ends as a transfer timeout. Analysis of the original CH376 firmware history (commit 5eb8385 of the MSXUSB project): the CH376 versions sent real bus resets before the first command (HW_RESET, a second reset in the Windows-like enumeration, and a reset on every error), while `hcd_port_reset()` of the RP2040 driver is an empty stub, so a drive connected directly to the Pico is never reset.
- BIOS: new boot self test (`BOOT_SELFTEST` in `config.asm`, disabled by default) that runs TEST UNIT READY, READ FORMAT CAPACITIES and READ CAPACITY on a floppy drive and prints `AA DD EE` (USB error, ASC, ASCQ), the first data bytes and, on failure, the `Diag:` line. Z80 test extended (101 checks).
- Docs: `docs/msx-picoverse-2040-msxusbfdd.md`, `docs/msx-picoverse-public-readme.md`, and the 2040 software README updated after hardware validation with both the TEAC FD-05PUB and TEAC USB UF000x drives.
- Firmware: the RP2040 host data-sequence error interrupt is disabled after `tuh_init()` (TinyUSB panics on it, which would hang core 1 and freeze the MSX).
- Diagnostics: a shared USB interrupt handler counts RX timeouts, sequence errors, stalls, completed transfers/buffers and connection events, and the controller endpoint registers (`int_ep_ctrl`, `sie_ctrl`, `sie_status`, `epx_buf_ctrl`, `int_ep_addr_ctrl[0..5]`, `int_ep_buffer_ctrl[0..5]`) are captured when a transfer times out. `PV_CMD_DEV_INFO` returns them in the data buffer and `PRINT_DIAG` prints them after the `Diag:` line as an `HW:` line (6 counters) and four lines of four 32-bit words. Z80 test updated.
- TEAC UF000x root-cause fixes (`pico/msxusbfdd/usb_host.c`, `CMakeLists.txt`, `tusb_config.h`, `msx/src/config.asm`, `msx/src/bank1/verbose_reset.asm`):
  - Per-device `ep0` max packet size (`--wrap=hcd_edpt_open`, `--wrap=hcd_setup_send`, `--wrap=hcd_edpt_xfer`): TinyUSB's `hcd_rp2040.c` shares a single `epx.wMaxPacketSize` across all USB addresses. When the 2-tier `0A05:7211` hub (whose `bMaxPacketSize0` is 8) enumerated its cascaded second hub chip on port 4 after the floppy drive on port 3, `usbh_edpt_control_open(0, 8)` overwrote `epx.wMaxPacketSize` from 64 to 8, splitting every 12-byte CBI `ADSC` command into `8 + 4` byte packets (which works on the TEAC FD-05PUB with `bMaxPacketSize0 = 8`, but corrupts the CDB on the TEAC UF000x with `bMaxPacketSize0 = 64`). `epx.wMaxPacketSize` is now saved per device address and restored before every control setup and data/status stage.
  - Compound 2-tier hub support (`tusb_config.h`): `CFG_TUH_HUB` increased from `1` to `2` so both internal `0A05:7211` hub chips enumerate cleanly instead of failing `TU_ASSERT(new_addr != 0)` in `enum_request_set_addr()`.
  - Bulk/interrupt endpoint STALL routing (`--wrap=hw_endpoint_reset_transfer`, `--wrap=hcd_event_handler`): `hcd_rp2040_irq()` always reported `USB_INTS_STALL_BITS` against `&epx` (EP0) even when EP0 was idle and an active bulk/interrupt endpoint in `ep_pool[1..15]` had stalled, turning any bulk-IN/OUT stall into a 10 s timeout instead of `XFER_RESULT_STALLED`. Stalls when `epx` is idle are now routed to the stalled endpoint in `ep_pool[1..15]`.
  - Endpoint transfer abort (`--wrap=hcd_edpt_abort_xfer`) and root-port bus reset (`--wrap=hcd_port_reset`, `--wrap=hcd_port_reset_end`): implemented real transfer abort for both `epx` and `ep_pool[1..15]` (restoring `next_pid` when an unconsumed buffer is aborted and preventing control-pipe wedging after a timeout) and root-port `USB_SIE_CTRL_RESET_BUS_BITS` bus reset with `USB_INTE_HOST_CONN_DIS_BITS` masked during SE0.
  - Selective endpoint halt clearing (`ufi_clear_ep_halt`) and interrupt polling interval: only the specific endpoint that stalled (or `ep_in` after a failed CBI read, matching the CH376 BIOS) is cleared and has its toggle reset, instead of clearing and reopening all three endpoints on every error; CBI interrupt `bInterval` is capped at 10 ms; `BOOT_SELFTEST` disabled by default in `config.asm` for normal MSX-DOS/BASIC boot.
  - High-rate `epx` Bulk IN/OUT engine, CBI status draining, and `DSKCHG` drive-number fix (`pico/msxusbfdd/usb_host.c`, `msx/src/bank1/dskio_dskchg.asm`):
    - Bulk IN (`0x82`) and Bulk OUT (`0x01`) transfers of UFI floppy drives are now executed directly on the RP2040's main asynchronous `epx` hardware engine (`ufi_bulk_epx` in SRAM) instead of TinyUSB's periodic `INT_EP` slots (`ep_pool[1..15]`). `INT_EP` only polls once per 1.000 ms SOF frame and does not retry on `NAK` until the next frame, which starves and overflows the FDC sector FIFO of streaming drives without a full-track buffer (such as the TEAC UF000x, which streams at 64 bytes per 1.024 ms) whenever the disk stream drifts across the SOF boundary, triggering Track-0 recalibrate grinding. `epx` retries `NAK` every 16 us and transfers multiple 64-byte packets per 1 ms frame like the CH376S and Windows.
    - When a CBI data stage stalls, `ufi_transport_cbi` clears the stalled bulk endpoint and still drains the 2-byte completion interrupt packet from `ep_int` (`0x83`) so a stale interrupt packet is never left in `0x83` to desynchronize `REQUEST SENSE` and subsequent commands after a disk error or disk change.
    - In `ufi_execute()`, valid 18-byte `REQUEST SENSE` data (`sense_len >= 14`) is preserved even when the drive's interrupt endpoint repeats the previous command's non-zero `ASC/ASCQ` (`sense_failed`), instead of being overwritten with `ASC = 44h`.
    - In `DSKCHG_IMPL` (`msx/src/bank1/dskio_dskchg.asm`), `WK_GET_LAST_REL_DRIVE` is called before `GETDPB_IMPL` so `GETDPB_IMPL` passes the valid drive number (`0` or `1`) to `DSKIO_IMPL` instead of `A = 0FEh` (`B - 1`), which previously caused `DSKIO_IMPL` to fail with `_DSKIO_ERR_PARAM` after a disk change.
    - Added a 300 us poll-alive watchdog (`last_poll_us` via `USB_SIE_STATUS_NAK_REC_BITS`) in `ufi_bulk_epx()` with 100 us `NAK_POLL` pacing while waiting for Packet 0 (`total == 0`, during spindle motor spin-up and track seek) and 16 us once streaming (`total > 0`), and restricted `ufi_clear_halts()` to bulk endpoints (`ep_in` and `ep_out`) so `ep_int` (`0x83`) toggle is only reset if `0x83` itself stalls.
